# HeartCode

HeartCode is a client-facing website builder platform: a client picks a website type, fills in a short form, gets AI-polished copy dropped into a live preview, and (starting in v1.0.4) pays to have the site deployed for real.

## Deploy this to Render

1. Push this repo to GitHub.
2. Render dashboard → **New → Web Service** → connect the repo. Build command: **`npm install && npm run build:css`** — not just `npm install` anymore as of v1.0.7 (see "Build command" note below; missing this half breaks every public page's styling). Start command: `npm start`.
3. Add every env var from the table below under the service's **Environment** tab.
4. Provision a Postgres database on Supabase or Aiven, and paste its pooled connection string into `DATABASE_URL`.
5. Deploy.
6. Hit `https://<your-app>.onrender.com/health` — confirm `{ "status": "ok", "db": "connected" }`.
7. Visit `https://<your-app>.onrender.com/<ADMIN_PATH_SLUG>/login` and log in with `ADMIN_USERNAME` and `ADMIN_PASSWORD`.

Full step-by-step walkthrough with more detail and troubleshooting: see `DEPLOYMENT.md`.

### Build command — read this if you're updating an existing Render service

As of v1.0.7, the public-facing pages (landing page, type gallery) are styled with Tailwind CSS, compiled ahead of time into `public/styles/main.css` by a build step — it is **not** checked into the repo as the source of truth; `src/styles/main.css` is the real source, and `public/styles/main.css` is generated from it. As of v1.0.8, the admin dashboard got the same treatment as its own separate bundle (`src/styles/admin.css` → `public/dashboard-assets/admin.css`, via `tailwind.admin.config.js`) — **the Render Build Command itself does not need to change again**: `npm run build:css` (already in place since v1.0.7) now runs both `build:css:public` and `build:css:admin` in sequence.

If you already have a Render service running from before v1.0.7, you still need to **update its Build Command** in the Render dashboard (Settings → Build Command) from `npm install` to:
```
npm install && npm run build:css
```
This is a setting on the Render service itself, not something in the repo — updating the code alone (applying a version's zip) does **not** change it. If you forget, neither CSS bundle gets (re)generated on that deploy, and the entire site — public pages AND the admin dashboard — loads with no styling.

As a safety net, this delivery includes both bundles already built and committed alongside the source files — so the site won't be broken even if you deploy without the correct build command. But they'll go stale the moment any future change touches the Tailwind source files or view markup, so get the build command right rather than relying on this indefinitely.

## Tech stack

- Node.js + Express (CommonJS)
- PostgreSQL via `pg`, hosted on Supabase or Aiven
- EJS server-rendered views for both the admin dashboard and the public builder flow
- Tailwind CSS (CLI-compiled) for BOTH the public site and (as of v1.0.8) the admin dashboard — two separate configs/bundles (`tailwind.config.js` + `src/styles/main.css` for public, `tailwind.admin.config.js` + `src/styles/admin.css` for admin), sharing one palette/font source (`tailwind.theme.js`) but compiled independently so neither bundle carries unused classes from the other surface
- Deployed on Render (see `DEPLOYMENT.md`)
- Generated client sites deploy live to Cloudflare Pages, paid for via Paystack

## Environment variables

Not every variable is required — two have safe defaults. The table below reflects what the code actually does with each one, not just what's in `.env.example`.

| Variable | Required? | Purpose | Where do I get this? |
|---|---|---|---|
| `DATABASE_URL` | Required | PostgreSQL connection string | From your Postgres provider (Supabase/Aiven) |
| `PORT` | Optional | Port the server listens on — defaults to `3000` if unset, and Render overrides it automatically anyway | Leave it unset |
| `NODE_ENV` | Optional | Runtime mode (`development`/`production`) — not currently read by any of HeartCode's own code, but standard practice to set on Render | Type `production` |
| `ADMIN_USERNAME` | Required | Admin login username | Type anything you'll remember |
| `ADMIN_PASSWORD` | Required | Admin login password, typed directly | Type your real password — no tool, no hashing |
| `SESSION_SECRET` | Required | Signs session cookies and derives CSRF tokens | Any long random string — a password generator app works fine |
| `ADMIN_PATH_SLUG` | Required | Secret URL segment where the admin dashboard lives | Make one up yourself, e.g. `raven-portal-92` |
| `ENCRYPTION_KEY` | Required | Encrypts Paystack/AI provider secrets at rest | Any string, any length — type a memorable phrase |
| `CLOUDFLARE_API_TOKEN` | Required | Deploys client sites to Cloudflare Pages | Cloudflare dashboard → My Profile → API Tokens → Create Token, with "Cloudflare Pages — Edit" permission |
| `CLOUDFLARE_ACCOUNT_ID` | Required | Identifies which Cloudflare account to deploy into | Cloudflare dashboard → any domain's Overview page → right sidebar under "API" |
| `RESEND_API_KEY` | Optional (v1.1.1+) | One-time migration only — see below | Resend dashboard → API Keys → Create API Key |
| `EMAIL_FROM_ADDRESS` | Optional (v1.1.1+) | One-time migration only — see below | Any address on a domain you've verified in the Resend dashboard first |

A few notes on what "Required" means in practice, since the failure modes differ:
- Missing `DATABASE_URL` — the app won't boot at all (`initDB()` fails fast, `process.exit(1)`).
- Missing `SESSION_SECRET` — the app boots fine, but crashes the request on the first login/session attempt.
- Missing `ADMIN_PATH_SLUG` — the app boots fine, but the entire admin dashboard becomes silently unreachable (404 everywhere, by design — no fallback to a guessable path).
- Missing `ADMIN_USERNAME`/`ADMIN_PASSWORD` — the app boots fine, but login will never succeed.
- Missing `ENCRYPTION_KEY` — the app boots fine, and read-only admin pages still load, but saving a Paystack key, AI provider key, or email provider secret will fail.
- Missing `CLOUDFLARE_API_TOKEN`/`CLOUDFLARE_ACCOUNT_ID` — the app boots fine, checkout and payment still work, but the deployment step fails right after payment succeeds (the client's money is taken and the deployment simply doesn't happen — set these before accepting real payments).
- `RESEND_API_KEY`/`EMAIL_FROM_ADDRESS` (as of v1.1.1) — **no longer required for normal operation.** Email sending is now configured entirely through the Email Providers admin page (Resend, Gmail SMTP, Brevo SMTP, or Generic SMTP — pick one, add it, send a test email, activate it). These two env vars now serve exactly one purpose: if `RESEND_API_KEY` is set AND the Email Providers table is still completely empty (i.e. you're upgrading from before v1.1.1 and haven't added anything through the new admin page yet), the app automatically migrates it into an active Resend provider the first time it boots after upgrading — so upgrading doesn't silently stop your existing email from sending. Once you've confirmed email is working (either the auto-migrated one, or a provider you added yourself), these two env vars can be removed from Render entirely. One thing worth knowing: that auto-migration check runs on every boot, not just once — if you later delete every provider row while `RESEND_API_KEY` is still set, it'll come back on the next restart. That's intentional (a safety net against accidentally ending up with zero configured providers), not a bug — just remove the env var once you're sure you don't want it.

### Getting each value — no computer or terminal needed

Everything below assumes you're setting these directly in Render's dashboard (Environment tab), on your phone.

- **`ADMIN_USERNAME`** — type anything, e.g. `advay`.
- **`ADMIN_PASSWORD`** — type your real admin password, directly. No hashing, no tool — the app compares it as-is at login time.
- **`ADMIN_PATH_SLUG`** — type any word or short phrase nobody would guess, e.g. `wolfden-42`. No special characters needed beyond letters, numbers, and hyphens.
- **`SESSION_SECRET`** and **`ENCRYPTION_KEY`** — both just need to be long and unpredictable. Easiest option: open any password generator app (or a site like a password manager's built-in generator), generate a 40+ character password, and paste the same one into both fields (or generate two separately — either is fine, they don't need to match each other). If you ever do have Node/a terminal handy, `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"` works too — it's just no longer required.

That's every value from the previous versions — nothing there needs a separate generation step or a website. `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` do each need a quick trip to Cloudflare's dashboard — works fine from a phone browser, no computer needed, just an extra step beyond "type something." As of v1.1.1, email no longer needs any env var at all — see "Configuring email providers" below.

### Configuring email providers (v1.1.1+)

Instead of one hardcoded Resend API key, email now goes through the **Email Providers** admin page (in the "System" section of the sidebar, next to AI Provider). You can add as many as you like and switch between them; exactly one is "active" at a time, and that's the one actually used for every outgoing email.

Four options, all from your phone, no terminal:

- **Resend** — same as before: an API key and a from address on a Resend-verified domain.
- **Gmail SMTP** — host/port/security are pre-filled for you. You'll need an **App Password**, not your normal Gmail password (Google account settings → Security → 2-Step Verification → App passwords). A regular password will be rejected by Google.
- **Brevo SMTP** — host/port/security are pre-filled for you (Brevo's free tier is a reasonable option if you don't want to verify a domain with Resend). Get SMTP credentials from Brevo's dashboard under SMTP & API.
- **Generic SMTP** — for any other provider (a hosting company's mail server, another transactional email service, etc.) — fill in the host, port, and security mode yourself.

After adding one, use the **Send test email** button on its card before activating it — this sends a real email through that exact configuration, so a wrong password or host shows up immediately instead of during a real client's deployment. Once a test succeeds, tap **Set as active**.

If you're upgrading from before v1.1.1 and already had `RESEND_API_KEY` set, you don't need to do anything — see the note above about the automatic one-time migration.


## Local setup (optional — only needed if you're developing with Node installed on a computer; not required to deploy)

```bash
git clone <repo-url> heartcode
cd heartcode
npm install
cp .env.example .env
```

Fill in `.env` using the table and guidance above, then:

```bash
npm run build:css
npm start
```

`npm run build:css` compiles both Tailwind bundles (`src/styles/main.css` → `public/styles/main.css` for public pages, `src/styles/admin.css` → `public/dashboard-assets/admin.css` for the admin dashboard, as of v1.0.8) — needed once before first run, and again any time you change either source file, either `tailwind*.config.js`, or add new Tailwind classes to any view. There's no watch mode wired up; re-run it manually after each such change during local development. `npm run build:css:public` / `npm run build:css:admin` run just one bundle at a time if you only touched one side.

The server runs `initDB()` on every boot, which creates/updates all tables and is safe to run repeatedly — it fails fast (`process.exit(1)`) rather than serving traffic against a broken database.

Once running, visit `http://localhost:3000/` for the public builder flow, or `http://localhost:3000/<ADMIN_PATH_SLUG>/login` for the admin dashboard. A fresh database has no website types yet, so the homepage will show "nothing available right now" until you create one from the dashboard.

## Project structure

```
db/         — database bootstrapping: init.js (schema, migrations, getPool())
lib/        — framework-free helpers: crypto, auth, ai-provider, paystack, template
              substitution (incl. v1.0.6 loop syntax), currency conversion,
              geolocation, rate limiting, Cloudflare Pages deployment, email,
              deployment finalization, the site-password bridge cache, site
              settings + site scripts + landing content reads (cached),
              icon loading, slug sanitization (shared, v1.0.8), deploy slug
              pattern resolution (v1.0.8), field type constants (v1.0.8)
middleware/ — Express middleware: admin slug gating, session auth, CSRF
routes/     — route handlers, split by area: admin pages, admin API (by
              feature — paystack, ai-providers, website-types, dashboard,
              settings, site-settings, scripts, landing (v1.0.8)), public
              pages (incl. checkout, landing page, type gallery), public
              build API, the Paystack webhook
views/      — EJS templates, split into admin/ (dashboard) and public/
              (client-facing landing page, type gallery, builder + checkout flow)
public/     — static assets: dashboard-assets/ (admin.css + admin.js, BOTH
              Tailwind-built as of v1.0.8), site.css/site.js (public builder
              flow), site-interactions.js (scroll-reveal/count-up), icons/
              (40 bundled Lucide SVGs), styles/main.css (BUILT from
              src/styles/main.css — see "Build command" above)
src/        — Tailwind sources: main.css (public — real source of truth for
              the public design system) and admin.css (v1.0.8 — same for
              the admin dashboard). Neither compiled output under public/
              should be hand-edited; both are generated.
```

  - **Real currency conversion.** `website_types.price_kes` was never actually KES — it was a raw number with a hardcoded "KES" label and zero conversion anywhere. It's replaced by `price_usd` as the real source of truth (the old column is left in place, unused, for backward compatibility — nothing reads it anymore). Prices are now geolocated and converted for display in the visitor's own currency (via `open.er-api.com`, cached and refreshed every 24h), with a strict rule: if no rate is available for a currency, the display always falls back to correctly-labeled USD rather than ever showing a raw number under the wrong currency code. A separate, real bug was also fixed in the same pass: the Paystack `currency` field was never being sent at all in earlier versions, meaning charges silently relied on whatever currency the Paystack account itself defaulted to, regardless of the number sent as `amount`. It's now sent explicitly, snapshotted at checkout time and never recomputed later (so a mid-flight exchange-rate refresh can't cause a mismatch at verification).

Each type can be individually switched on from its dashboard page (new "AI" tab), with its own system prompt, user-prompt template (built from that type's raw fields), and a set of "output fields" describing exactly what structured JSON to request back from the configured provider — flat text, a list of texts, or a list of objects with a defined shape. When a type has AI off, form submissions go straight to the template with zero AI calls and zero cost; the AI provider is never even queried. A lighter rate limit applies to non-AI types (20/hour) versus AI-enabled ones (5/hour, unchanged from earlier versions), since only the latter cost real tokens.
  - **Loop-capable templates.** Templates can now use `{{#each field}}...{{/each}}` to render a list-shaped AI output field — `{{this}}` for a list of plain text, `{{this.sub_key}}` for a list of objects. Saving a template now also warns (without blocking) if a flat placeholder is used against a list-shaped field, or vice versa, so a shape mistake is caught immediately rather than silently rendering blank on a live client preview.

- **v1.0.8** — Expanded field types, custom deploy slugs, a landing-page CMS, and a full admin redesign:
  - **Expanded field types.** Raw form fields can now be Number, Date, Radio (pick one), or Checkboxes (pick multiple), alongside the existing Text/Textarea/Email/Password/Dropdown. Every type gets real server-side validation on submit (not just "is it present") — a number must actually parse as one, a date must be a real calendar date (`2024-02-30` is correctly rejected, not silently rolled over to March 1st), and dropdown/radio/checkbox values must be a member of that field's own configured options. **That last check closed a real, pre-existing gap**: dropdown values were never checked against their configured options before this version, only checked for non-empty. Checkboxes (the one multi-value type) feed a template two ways from the same submitted array: `{{field_key}}` gives the values joined with `", "`, `{{#each field_key}}...{{/each}}` iterates them — reusing v1.0.6's loop syntax unchanged.

Checked against `deployed_sites` for a collision regardless of whether the pattern includes a `{{random}}` token of its own, with a random suffix appended only if one's actually found — a pattern with no random component at all stays perfectly clean unless two clients genuinely submit the exact same values. A pattern referencing a field that doesn't exist yet warns (doesn't block) at save time, the same way template placeholder mistakes already do. Long admin-entered text (script contents, AI output field descriptions) gets a "Show more" toggle instead of blowing out a layout. Deliberately more restrained than the public site's visual language — rectangular controls, not pills; modest rounded corners, not the public site's signature asymmetric shape — since this is a working tool, not a marketing surface.

    - Every opacity-modified color utility across the **entire public site delivered in v1.0.7** (`text-hc-ink/60`, `bg-hc-blue/10`, and every other `/NN` variant throughout the landing page, type gallery, and shared nav/footer) was silently never generated by Tailwind at all — not a wrong shade, simply absent — because the color tokens were defined pointing at a plain hex-string CSS variable, which Tailwind can't blend an alpha channel into. This means **the live v1.0.7 site has been missing a layer of intended color styling** since it was deployed; this fix corrects it going forward.

Never caught before now because every prior round of testing mocked this function out rather than exercising its real logic end-to-end; building this version's custom-slug feature required a faithful mock for the first time, which is what surfaced it. Fixed at the call site (the redundant prefix is now stripped before the seed is passed in), and the project-name length cap was raised from 20 to 40 characters in the same pass — the old cap silently truncated anything past it, which would have gutted most realistic custom slug patterns.

- **v1.1.0** — Pending-deployment recovery, and a first-party, privacy-conscious conversion funnel:
  - **Pending-deployment recovery (new "Recovery" admin page).** Previously, if a payment genuinely succeeded but the Paystack webhook never fired *and* the client never landed back on the confirmation page, the underlying `pending_deployments` row was swept away by the cleanup job within about 15-75 minutes — the payment was gone, no site ever got deployed, and there was no way to find or fix it afterward. That row is now kept for a full **7 days** before cleanup instead, giving an admin a real window to notice and recover it. The Recovery page lists every pending row (searchable, paginated), computing a clear `Active` / `Needs attention` status per row (whether its normal 1-hour checkout window has already closed). A **"Check & Deploy"** button re-runs the exact same verify → deploy → email pipeline the webhook and callback page already use — genuinely safe to click on any row, including one that was never actually paid: real Paystack verification happens first, and nothing is touched unless that verification actually succeeds. This needed one real architectural change, not just a longer cleanup timer: the deploy pipeline (`lib/finalizeDeployment.js`) already had an `expires_at`-based short-circuit that returned "expired" immediately, without even checking Paystack, for anything past its 1-hour window — which is exactly every row this feature exists to help with. A new `skipExpiryCheck` option (default `false`, unchanged for the webhook and the public callback page) is now the ONLY thing that bypasses that short-circuit, and only the new admin retry route ever passes it — an authenticated admin deliberately clicking the button, never the public unauthenticated callback URL. A row can also be deleted outright once confirmed genuinely abandoned.
  - **Funnel analytics (new "Funnel" admin page).** Tracks six stages of the client journey — home view, explore view, form started, preview generated, checkout started, payment completed — as a simple first-party event log (`funnel_events`), viewable over the last 7/30/90 days with an optional per-website-type filter, shown as plain proportional bars with the drop-off percentage between each consecutive stage. **No personal data of any kind is collected**: the identifier grouping a visit's events is a random, client-generated id living only in that tab's `sessionStorage` — not a persistent cookie, never tied to an email address or IP, gone the moment the browser session ends. Five of the six events are fired client-side, fire-and-forget, via `navigator.sendBeacon`; the sixth, `payment_completed`, is fired **only** from inside the real deploy pipeline itself (`lib/finalizeDeployment.js`) once a deployment has actually, verifiably completed — the public event endpoint (`POST /api/events`) explicitly refuses to accept that event type from a client, since a client-submitted "I paid" event would be trivially fakeable and pointless to chart. `checkout_started` fires on checkout **page load** rather than on the preview page's "Deploy this site" click — chosen for consistency with every other stage (all page-load signals) and because a click can happen without the visitor actually reaching checkout (e.g. missing preview data redirects back to the build form instead), which would overstate how many visits genuinely got there. One honest, inherent limitation surfaced in the UI itself rather than hidden: home and explore views are two *parallel* entry points into the site, not sequential steps of one path, so a visit can skip straight to explore (or straight to a shared `/build/:slug` link) without ever hitting home — meaning the "drop-off" between those first two stages can legitimately be negative (explore outpacing home), and filtering by website type always zeroes out both, since neither is tied to a specific type. This needed the same kind of architectural fix v1.0.8 and v1.0.9 each needed in turn: `payment_completed` fires from server-side code running well after the original page load that generated the session id, so that id is carried through checkout the same way `raw_field_values` (v1.0.8) and `ai_output_values` (v1.0.9) already are, via a new `pending_deployments.funnel_session_id` column — NULL-safe throughout, so an older pending row or a visit with JS/storage blocked just skips that one event rather than breaking anything.
  - **One real, notable interaction found and documented, not silently left as a surprise:** the in-memory cache holding a client's plaintext site password between checkout and the confirmation email (`lib/sitePasswordCache.js`) still ages out after its original 1 hour — deliberately *not* extended to match pending_deployments' new 7-day window, since a plaintext password has no business sitting in memory for a week. The one real consequence: recovering a payment more than about an hour after the original checkout attempt means the confirmation email won't be able to remind the client of a password they set (the deployed site's password gate itself is completely unaffected either way — it checks the hash stored in the database, never this cache).
- **v1.1.1** — Clean deployment URLs, a friendlier success page, multi-provider email, and a real geolocation diagnosis:
  - **Cloudflare Pages now hands clients a clean, permanent URL.** Every deployment was previously returning wrangler's per-deployment hashed URL (e.g. `https://e1c63c4b.hc-foo.pages.dev`) as *the* site address — correct, but a confusing thing to hand a client (why does my website start with a random hex string?), and not actually the stable address of the project going forward. Since the Cloudflare project is always created with `--production-branch=main` and every deploy explicitly targets `--branch=main` (the same value), every deployment this app makes is a production deployment by Cloudflare's own branch-matching rule — so the plain `https://<project-name>.pages.dev` alias is always the right, permanent one. That's what gets returned, stored, and emailed now; the hashed URL is still checked for internally (as a "did wrangler actually report success" signal) but never surfaces past that point. Carried-over caveat: a real, successful Cloudflare deploy still hasn't been exercised end-to-end in this sandbox (no network path to `api.cloudflare.com` here) — treat the first real deploy after upgrading as the actual proof; confirm the clean URL loads the site before trusting it broadly.
  - **Deployment success page no longer looks instantly clickable before it's actually safe to click.** The site link (both the plain URL text and the "Visit your site" button) is now disabled for a 20-second countdown ("Finishing up... 20s") before becoming clickable — a deliberate short buffer against a client tapping through before a brand-new Cloudflare Pages deployment has finished propagating, which would otherwise just look like a broken link for no visible reason. A permanent note was also added underneath: a reminder to check spam/junk for the confirmation email and mark it "not spam."
  - **Email sending moved off a single hardcoded `RESEND_API_KEY` and into a new Email Providers admin page** (System section of the sidebar, next to AI Provider) — the same "add one or more, mark one active" shape as AI Provider config, not a new pattern. Four options: Resend (unchanged, just moved into the DB), Gmail SMTP and Brevo SMTP (both pre-fill known host/port/security settings), and Generic SMTP for anything else — all three SMTP options are the same underlying provider type, differing only in what the form pre-fills. Every provider (not just the active one) can be sent a real test email before being activated, so a wrong password or host shows up immediately rather than during a real client's deployment. Upgrading is graceful: if `RESEND_API_KEY` is still set in your environment and no provider has been configured yet, the app automatically migrates it into an active Resend provider the first time it boots on this version — verified directly (fresh boot with `RESEND_API_KEY` set and an empty table auto-seeded exactly one active provider; a second boot afterward correctly did *not* re-seed a duplicate). Full secrets-convention parity with the existing Paystack/AI-provider admin pages: only the sensitive sub-field within each provider's config is encrypted at rest, masked in every API response, and a blank field on update means "leave it unchanged," never "clear it silently." **One real bug found and fixed while testing this feature, not left as a surprise:** the SMTP send path (via `nodemailer`) had no connection/greeting/socket timeout configured — reproduced directly against an unreachable host, it hung the request **indefinitely** rather than failing, the first time this codebase has ever made a raw TCP connection instead of an HTTP `fetch()` (which fails fast through normal HTTP error handling). Fixed with explicit 10s/10s/20s timeouts; re-tested against the same unreachable host and confirmed it now fails cleanly in exactly 10 seconds with a readable error, without affecting any other request the server is handling. This mattered for more than just the "send test email" button, too: `lib/finalizeDeployment.js` holds a Postgres row lock for the full duration of the site-ready email send (see `HANDOFF.md`'s Key Decision #3) — an unbounded hang there would have blocked a legitimate retry of that same deployment reference indefinitely.
  - **Diagnosed, and hardened against, a real currency bug:** Kenyan visitors were reportedly always seeing USD pricing regardless of the admin toggle. Root-caused to `lib/geolocation.js` relying on a single free provider (`ip-api.com`) with a strict 45-requests-per-minute cap **per source IP** and an HTTP-only free tier — a real risk on a platform like Render that can pool multiple customers' outbound traffic behind a shared IP, where one busy neighbor could exhaust that shared IP's quota for everyone silently. A systemic geolocation failure and an ordinary non-Kenyan visitor look byte-for-byte identical from the outside (both just quietly get USD), so this was invisible without deliberately looking for it. Fixed with a second, independent fallback provider (`ipwho.is` — different host, native HTTPS, a much higher free quota) tried only when the first genuinely fails, plus a new low-noise log line on every fresh (non-cached) resolution so a real outage is now visible in Render's own logs going forward. A new "Geolocation health check" panel (Payments admin page) runs a live, uncached lookup on demand and shows exactly what happened with each provider — verified working end-to-end against real requests, including confirming the existing 1-hour cache still correctly suppresses duplicate log lines for the same visitor. **Honest limitation:** this diagnosis is reasoned from the code and public information about `ip-api.com`'s rate-limit policy, not confirmed against Render's actual production network — this build sandbox has no way to reach either geolocation provider to observe Render-specific behavior firsthand. The new diagnostic panel exists specifically to let you get that real, first-party confirmation yourself, from your phone, without a terminal.
- **v1.1.2** — SEO fundamentals, real-time sale notifications, and self-service site-details recovery:
  - **SEO fundamentals.** `/sitemap.xml` (currently-active website types only — an inactive type's `/build/:slug` 404s, so listing it would be a dead end for a crawler) and `/robots.txt` (allows everything except `/api/*` and the checkout/preview flow, and points at the sitemap) are both dynamically generated on every request straight from live DB state — no caching, no build step. Every website type can now optionally override its own `/build/:slug` page title and meta description (Website Types → a type → Details tab → "SEO overrides") — left blank, a type keeps using the site-wide title/description exactly as before; verified both the override and the fallback-when-cleared path directly. The homepage now carries Organization + WebSite JSON-LD (built from existing Site Settings values, no new admin input needed); every `/build/:slug` page carries Product JSON-LD with the real, canonical USD price — deliberately never the visitor's locally-converted display price, since structured data needs one stable value regardless of who's crawling from where. **Keeping the admin login page out of Google:** the first pass listed the secret admin path directly in `robots.txt`'s `Disallow` rules, which was flagged and then deliberately revised — `robots.txt` is a public, unauthenticated file, so that approach handed the exact "secret" path to anyone who thought to check it, not just search crawlers. Replaced with an `X-Robots-Tag: noindex, nofollow` response header, set once in `middleware/adminSlug.js` at the same point the slug match itself succeeds — so it covers the login page (reachable, and therefore indexable, without any credentials) as well as every authenticated page behind it, without ever publishing the path anywhere public. Verified directly: `robots.txt` no longer mentions the slug at all, the header is present on both the unauthenticated login page and an authenticated admin page, and is correctly absent from public pages.
  - **Real-time sale notifications** (new Notifications admin page, System section) — get pinged the moment a sale completes and a site deploys, across up to three simultaneous channels: up to 3 email addresses, 1 webhook (POSTs a plain JSON payload — `event`, `websiteType`, `clientEmail`, `siteUrl`, `amount`, `currency`, `deployedAt` — to any URL, auth token embedded in the URL's query string if the endpoint needs one), and 1 Gotify server. Per-type caps enforced the same row-locked way as v1.0.7's script-manager cap. Every channel fires **independently** (`Promise.allSettled`, not `Promise.all`) — verified directly by triggering all three types with credentials this build sandbox can't actually reach: all three failed on their own external call, all three were logged individually with channel id/type/label, and the function still resolved cleanly rather than throwing. Fires from `lib/finalizeDeployment.js` in its own try/catch, completely independent of the client's own confirmation email, and only ever after that function's transaction has already committed — a slow or failing channel here can only delay the HTTP response that triggered it, never the deployment itself and never the Postgres row lock that guards deployment idempotency. Applied the same lesson v1.1.1 learned about `nodemailer` hanging with no timeout: both the webhook and Gotify calls go through an `AbortController`-bounded `fetch` (10s), even though `fetch`'s normal HTTP error handling usually fails fast on its own. Every channel can be sent a real test notification before being relied on.
  - **Resend Site Details** (new public page, `/resend-details`) — a client who lost their confirmation email can request it again by email address, no account system needed. Rate limited per IP against an **admin-configurable** daily cap (Site Settings page, default 1/day) — the first rate limit in this app an admin can tune without a code deploy, read fresh from the database on every single request rather than cached, verified by changing the limit and confirming the very next request respected it immediately. **Anti-enumeration by construction**: a match and a no-match return the exact same 200 response, byte-for-byte — verified directly side by side. A DB error or an email-delivery failure both silently fall through to that same generic response rather than surfacing differently (a malformed email *format*, which reveals nothing about whether any real address has ever purchased anything, is the one deliberate exception, returning its own 400). Lists every matching site if a client purchased more than once. **One real, pre-existing gap found and fixed while building this, not something this feature caused:** `deployed_sites` never actually recorded whether a site was password-protected — the only copy of that fact lived in `pending_deployments.site_password_hash`, deleted the moment a deployment finalizes. Added `deployed_sites.has_password`, populated going forward; **honestly, this cannot be backfilled** — any site deployed before this column existed will incorrectly appear password-free in a resend-details email, not because the code is wrong, but because the underlying fact was never persisted anywhere retrievable for those rows.
- **v1.1.3** — Homepage redesign: a flexible, section-based landing-page CMS, restyled using a purchased Skilline HTML template as the visual/motion source, recolored entirely into this app's existing hc-blue/hc-yellow palette:
  - **This build started from an already-partial previous attempt, not a blank slate — and corrected its design.** The repo this version was built from already had a `landing_sections` table, `lib/landingSectionTypes.js`, and a full admin CRUD API wired up and nav-linked, but the actual redesigned page had never been built (the live homepage was still the v1.0.7 layout), and — more importantly — the section content schemas modeled images as an admin-editable hosted `image_url` string. That's a real design mismatch with this version's actual requirement: every image is a **fixed, already-committed file** (`public/images/landing/`, 14 files copied and renamed from the Skilline template, excluding its fake company-logo strip, the four images used only by its dropped "Latest News" section, and one genuinely unused file — `hero.png` — that isn't even referenced by the template's own markup), referenced by an immutable `image_asset_key` that's set only at seed time and can never be changed through the admin UI — enforced server-side (`lib/landingSectionTypes.js`'s `preserveImageAssetKeys()`), not just by leaving the field off a form.
  - **Seven section types**, each independently addable/reorderable/toggleable/deletable from the new **Landing Sections** admin page: `hero`, `feature_cards`, `split_image_text` (covers five distinct "image + heading + paragraph" template sections plus a sixth — the template's "Integrations" block, not explicitly named in this version's original spec catalog but visually the same shape, included rather than silently dropped), `cta_image_cards`, `bullet_list`, `testimonials` (ships with zero seeded items **on purpose** — never placeholder people — and correctly renders nothing at all on the public page until at least one real testimonial exists; verified both states directly), and `footer`. The always-on stats counter and the website-type teaser grid are deliberately **not** part of this CMS — they're kept as fixed sections on the page, unchanged from v1.0.7/v1.1.0: this version's brief explicitly says not to rebuild the stats counter under a different name, and removing the type grid would functionally gut the page's only path into `/build/:slug`, which is out of scope for a visual redesign.
  - **New `sk-*` color tokens** (`tailwind.config.js`, landing-bundle-only — never touches `tailwind.theme.js`, so the admin dashboard's separate CSS bundle can't pick them up) are each a computed tint or shade of the *existing* `hc-blue`/`hc-yellow`, not any of Skilline's own template colors — the deliberate one-to-one recolor this version's brief called for. Same RGB-triplet custom-property pattern as `hc-blue`/`hc-yellow` (`--sk-*-rgb` in `src/styles/main.css`), for the same reason documented since v1.0.8: a plain hex custom property silently breaks Tailwind's opacity-modifier utilities (`bg-sk-blue/10` etc.). **A real instance of exactly that failure class was caught and fixed before shipping, not left as a landmine:** several partials build a color class from admin content at runtime (`` `bg-${icon_color}/10` ``) — Tailwind's JIT scanner only ever generates classes it can find as literal text in the files it scans, so a runtime-interpolated class name is invisible to it and silently produces no CSS. Fixed with an explicit `safelist` regex covering every `bg-`/`text-`/`border-` combination (with and without opacity suffixes) of every `sk-*` token — verified by actually running the Tailwind CLI against the new config and confirming `bg-sk-blue/10` compiles to `background-color: rgb(var(--sk-blue-rgb) / 0.1)` in the real output, not just reasoning about it.

An early pass through `views/partials/landing-sections/footer.ejs` displayed that migrated value as a blurb near the logo *and* a separately hardcoded copyright bar underneath — for the real, actual seeded content on this app, that put a near-identical copyright notice on the page twice. Caught by rendering the real migrated homepage against a real local Postgres instance and reading the output, not by inspection. Fixed by giving the migrated value sole ownership of the bottom bar, matching exactly where the pre-redesign footer partial already displayed this same column.

Rewritten so each row wires its own nested array exactly once, at the moment that row is created, with no path that ever re-wires an element twice — verified with a real jsdom harness driving actual click events end-to-end (add two columns, add/remove links in both the original and a freshly-added column, submit, and assert the exact resulting row counts and saved JSON shape at each step), not just re-reading the new code and reasoning it should work.
  - **Testing note, honestly stated:** this build was verified against a real local Postgres instance and a real running server (fresh-DB migration, homepage render, full admin CRUD including move/toggle/delete, an attempted `image_asset_key` injection correctly rejected server-side, and HTML tag-balance checked programmatically) plus real jsdom-driven tests of the admin JS's DOM behavior specifically because the two bugs above were real and would not have been caught by reading the code alone. What could **not** be verified, same limitation as every prior version: this sandbox has no working headless browser, so the actual responsive layout at real breakpoints has not been visually confirmed — only that the HTML is well-formed and every element that should be present is present.

The old **Landing Page** admin page has been trimmed down to match — it used to also manage hero text, the trust line, and steps, none of which affect anything visible anymore now that the homepage renders from `landing_sections` instead; those controls were removed rather than left as confusing dead inputs. `routes/adminLanding.js`'s corresponding hero/step *endpoints* are left as-is server-side — reachable only by hand-crafted API calls now that no UI links to them, which felt like a smaller, more honest footprint than also tearing out otherwise-harmless working code this version didn't need to touch.

## What's next

The items flagged in `HANDOFF.md`'s "Known gaps" mostly remain open. Most notably: **there's still no global Express error-handling middleware wrapping every async route handler** — v1.1.1 added a targeted timeout fix to the one SMTP call site actually reproduced hanging, and v1.1.2's webhook/Gotify calls were built with a timeout from the start specifically because of that lesson, but neither is a systemic fix. This gap is demonstrably real, not theoretical, and remains the single most valuable thing to prioritize in a future version. The Cloudflare Pages deploy path (including v1.1.1's clean-URL fix) still hasn't completed a real successful deployment in testing — worth a deliberate first real-world check with actual credentials. v1.1.1's geolocation diagnosis is reasoned-through rather than confirmed against Render's real network/traffic — worth a real look once deployed. `views/public/preview.ejs` still has the duplicate `<script src="/site.js">` tag noted in v1.0.9. The v1.0.9 public restyle, and now v1.1.3's homepage redesign, still haven't been checked against a real browser at real breakpoints — this sandbox has no working headless browser, and that limitation is unchanged. v1.1.0's funnel data remains purely stage-level counts, not a per-visit multi-stage join. `deployed_sites.has_password` cannot be backfilled for anything deployed before v1.1.2 (see that version's changelog entry) — a resend-details email for an old password-protected site will incorrectly omit the "can't recover this" notice; there's no code fix for this, only awareness of it. The notification webhook's auth model (a token embedded directly in the URL's query string) is the simplest thing that works today, but is worth revisiting if a future integration needs something more structured (HMAC request signing, a custom header) — nothing in the schema prevents adding that later. New for this version: a section an admin creates fresh through the new Landing Sections page (rather than one seeded from the original template) has no image available to it at all — there's no image-picker/upload UI this version, by design, not oversight, but it does mean a brand-new `split_image_text`/`cta_image_cards`/`bullet_list` section renders with a neutral gradient placeholder instead of a real photo until a future version adds that capability.
